# INVARIANTS — sms-mail-multi

Ce fichier **s'ajoute** à `CHANTIERS.md` et **reprend** la section « Points à ne pas défaire » qui y figurait jusqu'au
27/11/2026 : sortie demandée par l'utilisateur (« Sort les invariants ») pour tenir `CHANTIERS.md` sous 30 Ko. Il ne remplace
rien d'autre. `CHANTIERS.md` garde l'état du travail et les décisions à trancher ; ici, ce qui ne doit pas être défait.

**Règle** : une tâche terminée sort de `CHANTIERS.md` ; son invariant (ce qui ne doit pas être défait, avec sa raison) est écrit ici,
dans la section du sujet. Lire la section concernée avant de modifier le code d'un sujet listé. Aucune donnée d'usager dans ce fichier.

## Données, dates, sauvegardes, RGPD

- **Aucune donnée d'usager dans un repo public.** Sauvegardes vers le repo privé `GH_REPO='maswaddpt47-cmyk/sms-mail-multi-backups'`, rétention 30 jours, la plus récente toujours gardée. Jeton GitHub : formulaire reconnu par Proton Pass (clé `ess-gh-token`) ; un effacement des données du navigateur l'efface.
- **Erreurs GitHub et état local** (22/11) : 401 jeton refusé, 403 droits, 404 dépôt inaccessible ou absent, réseau distingués (`ghMessageErreur`, test `check-erreurs-github.js`) ; une erreur de liste n'est jamais « aucune sauvegarde », un 404 de dossier est distingué par lecture du dépôt. Le « Sauvegardé le » de `persist` concerne l'enregistrement local, pas une preuve d'envoi GitHub.
- **Suivi des sauvegardes GitHub** (22/11) : panneau de Gestion des données mis à jour sans fermer la fenêtre ; dernière réussite via `gh-last-backup` (ce navigateur), envois prévus/en cours/erreurs en mémoire seulement (`_ghEtatSauvegarde`) ; une réponse ancienne ne masque pas un essai plus récent ; aucune promesse de couverture des modifications suivantes ni de synchronisation inter-appareils. Tests : `check-erreurs-github.js`.
- **Cloisonnement par profil** : toute donnée d'usager passe par `ess-<profil>-…` (`pk`/`pkFor`) ; migration ou archivage ne touche jamais un autre profil. Toute migration délicate mérite un test (une migration non testée a réduit 11 CMS à 6).
- **Rétention RGPD** (`archiveYear`) : agrégats anonymisés puis suppression irréversible du détail d'une année révolue, confirmation obligatoire. **Archives `ag017-v1`** : purge par cohorte (`entryYear`), contributions à leur date, fiches déjà comptées (`idsFiches`) et non réconciliées (`nonReconciliee`) exclues, recomptage indépendant (`recompterCohorte`) et invariants avant purge, lecture stricte, export de contrôle sans identifiant. Archives déjà calculées jamais recalculées (ancien comptage par fiche, lun.–ven.). Test : `check-archives.js`.
- **Dates et `ts`** (AG-016) : jour courant = `jourParis()` ; lecteurs de `ts` = `lireTs`/`afficherTs` ; nouvelles fiches `ts` = `tsParis()` (ISO avec décalage de Paris, pas `Z`) ; `ts` des mandats en texte français ; anciens `ts` jamais réécrits. `id` donné aux seules nouvelles fiches (`nouvelIdFiche`), jamais écrasé ; localisateurs : repli vers une unique fiche ancienne sans `id`. Tests : `check-stats-rdv.js`, `check-ecritures.js`.
- **Sens des champs** : `dateReception` = réception de la demande (facultatif, repris de `o.date` depuis Orientations) ; `dateDemande` = date du message, pas une réception ; `premierePreparationAt` = première préparation (depuis le 22/10) ; `date` = RDV ; orientation : `o.date` demande, `o.commune` structure, `o.motif` libre, `o.done` traitée, non archivées.
- **Réception** (AG-022, AG-023) : une ancienne `dateDemande` n'est jamais affichée ni préremplie comme réception ; seule une confirmation explicite l'enregistre ; un formulaire ne réécrit `dateReception` que si le champ a changé (`sourceReception`, `receptionAEcrire`) ; `receptionDateFor` ne sert qu'à la préparation moyenne. `dateDemande` ≤ 2026-10-22 sans `dateReception` = réception ancienne, comptée, borne non étendue. Tests : `check-ecritures.js`, `check-reception.js`, `check-delai-attente.js`.
- **Fiche sans message** : `body:''` explicite (ICS, planning) = pas un dossier, comptée à part ; sans champ `body` : comptée.
- **Lien orientation → dossier** (AG-033) : `orientationId` écrit à l'enregistrement (Générer et copie) seulement si nom et prénom sont ceux de l'orientation (`orientationALier`) ; `done` écrit dans la **même opération** que la fiche (`addHistory(item, prepared, lienOrient)`, retour arrière compris) ; à la fusion un lien existant n'est jamais remplacé ; « Traitée » = dossier préparé, pas envoyé ni réalisé ; anciennes fiches jamais réécrites ; export CSV inchangé. Carte : première fiche liée hors indisponibilité (`ficheDeOrientation`). Tests : `check-ecritures.js`, `check-orientation-lien.js`.
- **Confirmation avant tout remplacement de données** (25 et 27/11, validée ; pas de bloc AGORA) : « Importer JSON » et la restauration GitHub passent par `demanderImport` : vérification d'abord (invalide = rejet, rien d'écrit), puis fenêtre qui nomme le profil, annonce le remplacement (fiches, réglages communs, calendrier en événements et inscriptions, couleurs) et propose d'exporter ; Annuler, ✕ et fond = rien modifié ; `confirmerImport` refuse si le profil a changé et lance `apres` seulement après un remplacement réussi. **Tout nouveau chemin d'import appelle `demanderImport`, jamais `doImport`.** `countEvents` = événements regroupés comme l'écran, annulés compris, sans filtre (AG-037). Tests : `check-ecritures.js`.
- **Écritures sûres** (AG-013) : fiche, journée, pause déjeuner, compteur d'export (et orientation) enregistrés ensemble ou pas du tout (`operationHistorique`) ; `addHistory` renvoie true seulement si tout est écrit. Rappel « N messages non sauvegardés » toutes les 5 fiches, seulement sans jeton ou si `gh-last-backup` > 24 h ; `since-export` retombe à 0 après export ou sauvegarde.
- **Sauvegarde et calendrier** (AG-032) : sans `calendarIcs`, le calendrier n'est pas touché ; avec, il est remplacé ; vide écrit en clair ; invalide → import refusé ; sauvegarde auto différée ; restauration > 1 Mo en raw.
- **Doublons de fiche** (cause non identifiée) : dédoublonnage par date + heure + CMS (`cmsKey`) + nom + prénom ; une 3ᵉ occurrence passe le critère AGORA 3. Statut revenu en arrière (01/11, hypothèse : restauration d'une sauvegarde plus ancienne d'un autre appareil) : à rouvrir si le cas se reproduit.
- **Rappel de la veille : gardé, non utilisé** (`h.rappelVeille` pas tenu à jour) : ni donnée ni retrait.
- **Captures et sauvegardes** : jamais de données réelles envoyées à Claude ; diagnostic calculé dans le navigateur de l'utilisateur, nombres seuls à l'écran (règle 59).

## Agenda, créneaux, journées

Commune de « Ouvrir une journée » = liste déroulante.
